# Dashboard Build Spec

Implementation-ready spec for the internal agency dashboard. Reasoning and tradeoffs live in [[00-Dashboard-Architecture]]; this note is the part Claude Code builds from.

> [!note] Confirm the repo before writing any code
> `Design-of-Man/Jarvis` is the most likely home for this build — it already has "app metrics readiness for launch" work in it, including domain decisions. Confirm that before starting, and update this note once it's certain. Building a second dashboard next to a half-finished one is the expensive mistake available here.

---

## 1. Stack

| Layer | Choice | Why |
|-------|--------|-----|
| App | Next.js (App Router), TypeScript | Same stack as client sites — one toolchain |
| Hosting | Vercel | Same account and deploy flow as client sites |
| Database | Postgres (Supabase) | Operational state needs transactions and atomic upserts; Dropbox cannot provide either |
| Scheduling | Vercel Cron | Metric fetchers, reconciliation, expiry sweeps |
| Vault sync | Node watcher (`chokidar` + `gray-matter`) on the machine holding the Dropbox-synced vault | Vercel build containers cannot see the vault |
| Auth | Google OAuth (Auth.js) + Vercel deployment protection | Two internal users; no custom auth |
| Notifications | Slack Web API + interactions endpoint | Existing channel structure |

## 2. Data model

Postgres. Timestamps are `timestamptz`. Money is `numeric(12,2)` and nullable — the vault carries `$X` placeholders, and the app must render "not set" rather than 0.

### `clients`

Synced from `CLIENTS/*.md` frontmatter. The vault is the writer; the app treats this table as a read cache.

| Field | Type | Notes |
|-------|------|-------|
| `id` | text PK | Slug, e.g. `abacoa-podiatry` |
| `name` | text | |
| `domain` | text | Primary production domain |
| `status` | enum | `live`, `launch_ready`, `prospect`, `dormant`, `churned` |
| `stage` | enum | `prospect`, `pitched`, `evaluating`, `hot`, `live`, `lost`, `dormant` |
| `stage_since` | timestamptz | Drives aging and cohorts — see [[04-Pipeline]] |
| `owner` | text | `nick` \| `cam` |
| `industry` | text | |
| `vercel_project_id` | text nullable | Null ⇒ health row renders "not connected" |
| `gsc_property` | text nullable | Same rule |
| `repo` | text nullable | `Design-of-Man/<repo>` |
| `plan` | text nullable | Management tier |
| `mrr` | numeric nullable | Null until a real figure exists |
| `plan_value` | numeric nullable | Expected MRR for pipeline math |
| `go_live_date` | date nullable | |
| `open_issues` | int default 0 | |
| `vault_path` | text | Source file, for deep links |
| `content_hash` | text | Change detection for the sync |
| `synced_at` | timestamptz | Powers the staleness badge |

### `agent_runs`

Written by agents at start, updated at completion.

| Field | Type | Notes |
|-------|------|-------|
| `id` | uuid PK | The `run_id` everything else joins on |
| `agent` | text | `seo-audit`, `sales-outreach`, `copy-content`, `design-graphics`, `site-maintenance`, `client-support`, `client-reporting`, `skills-radar` |
| `client_id` | text nullable FK | Null for agency-wide runs like Skills Radar |
| `trigger` | enum | `schedule`, `manual`, `retry` |
| `task_class` | enum | `read` \| `write` — determines whether a lock is required |
| `status` | enum | `running`, `succeeded`, `failed`, `skipped_locked`, `cancelled` |
| `current_step` | text nullable | Powers the live "what is it doing" line |
| `started_at` / `finished_at` | timestamptz | |
| `heartbeat_at` | timestamptz | Also used to detect zombie runs |
| `summary` | text nullable | One line for the feed |
| `error` | text nullable | |
| `artifacts_created` | int | Approvals generated by this run |
| `changes_deployed` | int | |
| `log_path` | text nullable | `AGENTS/Execution-Logs/YYYY-MM-DD-<agent>-<client>-<run8>.md` |
| `tokens_used` | int nullable | Cost tracking through the AI gateway |

Indexes: `(client_id, started_at desc)`, `(status)` partial on `running`, `(agent, started_at desc)`.

### `client_locks`

One row per client. Mechanism and TTL reasoning in [[00-Dashboard-Architecture]] §4.

| Field | Type | Notes |
|-------|------|-------|
| `client_id` | text PK FK | One lock per client — this is the mutual-exclusion key |
| `holder_agent` | text | |
| `run_id` | uuid FK | Ownership check on release |
| `task_kind` | text | |
| `acquired_at` | timestamptz | |
| `expires_at` | timestamptz | **Required.** Never nullable — a null expiry is a permanent deadlock |
| `heartbeat_at` | timestamptz | Extends `expires_at` on live runs |
| `reclaimed_count` | int default 0 | Increment on stale takeover; a rising count means agents are crashing |

### `approvals`

| Field | Type | Notes |
|-------|------|-------|
| `id` | uuid PK | Carried in the Slack button payload |
| `run_id` | uuid FK | |
| `client_id` | text nullable FK | |
| `class` | enum | `sales_email`, `social_caption`, `social_graphic`, `seo_change`, `support_reply` |
| `status` | enum | `pending`, `approved`, `rejected`, `expired`, `superseded` |
| `title` | text | Queue line item |
| `body` | jsonb | Artifact payload — email body, caption text, image URL, SEO diff |
| `edited_body` | jsonb nullable | Set on approve-with-edits; original preserved in `body` |
| `content_hash` | text | Dedupe key with `(client_id, class)` |
| `assigned_to` | text nullable | `nick` \| `cam` \| null for the shared pool |
| `decided_by` / `decided_at` | text / timestamptz | |
| `reject_reason` | text nullable | **Required when status = rejected** (check constraint) |
| `expires_at` | timestamptz | Per-class window |
| `slack_channel` / `slack_message_ts` | text nullable | For `chat.update` and reconciliation |
| `slack_delivery_status` | enum | `pending`, `delivered`, `failed` |
| `supersedes` | uuid nullable FK | |
| `created_at` | timestamptz | |

Constraints that carry real weight:
- `check (status <> 'rejected' or reject_reason is not null)`
- Partial unique index on `(client_id, class, content_hash) where status = 'pending'` — makes retry-driven duplicates impossible at the database level, not just in application code.

### `metric_snapshots`

Cached external API data. Never fetched during a page render.

| Field | Type | Notes |
|-------|------|-------|
| `id` | bigserial PK | |
| `client_id` | text nullable FK | Null for agency-wide metrics like revenue |
| `source` | enum | `vercel_analytics`, `vercel_deploy`, `vercel_errors`, `gsc`, `post_bridge`, `qbo`, `uptime` |
| `metric` | text | `visitors_7d`, `clicks_28d`, `avg_position`, `revenue_mtd`, … |
| `value` | numeric nullable | |
| `value_json` | jsonb nullable | Top queries, deploy detail, and anything not scalar |
| `data_date` | date nullable | **The date the data describes.** For GSC this trails `fetched_at` by 2–3 days |
| `fetched_at` | timestamptz | |
| `fetch_status` | enum | `ok`, `stale`, `error` — an error keeps the last good row rather than blanking the tile |

Index: `(client_id, source, metric, fetched_at desc)`.

### `notifications`

Feed panel. Mirrors what agents sent to Slack so the dashboard is readable without opening Slack.

| Field | Type |
|-------|------|
| `id` uuid PK, `run_id` uuid nullable, `client_id` text nullable | |
| `level` enum | `info`, `warn`, `alert` |
| `channel` text, `message` text, `slack_ts` text nullable, `created_at` timestamptz | |

## 3. API surface

### Agent-facing (service token, `Authorization: Bearer $AGENT_TOKEN`)

| Method | Route | Purpose |
|--------|-------|---------|
| `POST` | `/api/agent/runs` | Start a run, return `run_id` |
| `PATCH` | `/api/agent/runs/:id` | Update step, heartbeat, finish, or fail |
| `POST` | `/api/agent/locks/:clientId` | Acquire — returns 200 with the lock, or **409 with the current holder** so the agent can log a meaningful skip |
| `POST` | `/api/agent/locks/:clientId/heartbeat` | Extend `expires_at` |
| `DELETE` | `/api/agent/locks/:clientId` | Release — ownership-checked on `run_id`, idempotent |
| `POST` | `/api/agent/approvals` | Create a pending approval; returns 200 with the existing id on a dedupe hit |
| `GET` | `/api/agent/approvals/:id` | Poll for a decision |
| `POST` | `/api/agent/notifications` | Push a feed entry |

### App-facing (session auth)

| Method | Route | Purpose |
|--------|-------|---------|
| `GET` | `/api/dashboard/summary` | Everything the home screen needs, one call |
| `GET` | `/api/clients` / `/api/clients/:id` | Roster and drill-down |
| `GET` | `/api/clients/:id/metrics?range=` | Snapshot history for charts |
| `GET` | `/api/runs?client=&agent=&status=` | Historical log view |
| `GET` | `/api/approvals?status=pending` | Queue |
| `POST` | `/api/approvals/:id/approve` | Body optionally carries `edited_body` |
| `POST` | `/api/approvals/:id/reject` | Reason required |
| `GET` | `/api/pipeline` | Stages, aging, cohorts |
| `GET` | `/api/health` | Own liveness + sync freshness + last successful fetch per source |

### Webhooks and cron (no session)

| Route | Auth | Purpose |
|-------|------|---------|
| `POST /api/slack/interactions` | Slack v0 signature; timestamp within 5 min; replay rejected | Approve/reject from Slack. Ack within 3s, process async |
| `POST /api/webhooks/vercel` | Vercel signature | Deployment events |
| `POST /api/sync/vault` | Service token | Watcher pushes parsed frontmatter batches |
| `GET /api/cron/fetch-vercel` | Vercel Cron header | Every 5 min |
| `GET /api/cron/fetch-gsc` | Vercel Cron header | Daily |
| `GET /api/cron/fetch-qbo` | Vercel Cron header | Every 6 hours |
| `GET /api/cron/uptime` | Vercel Cron header | Every 5 min |
| `GET /api/cron/reconcile-approvals` | Vercel Cron header | Every 10 min — recovers lost Slack interactions |
| `GET /api/cron/expire` | Vercel Cron header | Hourly — expire approvals, sweep stale locks, flag zombie runs |

## 4. Auth and access

Internal only. Two people. Design accordingly and do not build more than that.

- **Google OAuth** (Auth.js) restricted to an explicit allowlist of Nick's and Cam's Workspace accounts. Allowlist by full email address, not just the hosted domain — a domain check silently admits any future account on the domain.
- **Vercel deployment protection** in front of the whole project, including preview deployments. Previews of an internal dashboard are internal too.
- **Machine routes are separate from human routes.** Agent endpoints use a service token and never accept a session cookie; human endpoints never accept the service token. One token, rotatable, stored in Vercel env and in the agent runner's environment.
- **Webhook routes are public by necessity and verified by signature.** Slack requests are validated against the raw request body before parsing — a framework that parses the body first breaks signature verification.
- **No secrets in the vault.** The vault syncs through Dropbox. Credentials live in Vercel env vars, the agent runner's environment, and a password manager. See the warning note in `INTEGRATIONS/Credentials/`.
- **Audit trail.** Every approval decision records who and when. With two users this is not compliance theater — it is how you answer "did you send that, or did I."
- **No client or patient data beyond what's needed.** Clinic operations stay out of this app entirely.

## 5. Deployment

- **Vercel project**, separate from client sites, same team account. Production plus preview.
- **Supabase project** for Postgres. Migrations in-repo (`supabase/migrations`), applied through CI.
- **Vault watcher** runs where the Dropbox-synced vault lives. Ship it as a small Node service with a launchd/systemd unit so it restarts on boot. Fallback if keeping it alive proves annoying: a scheduled full re-import every 15 minutes — slower, dumber, nothing to crash.
- **Domain:** internal subdomain behind deployment protection. (A domain purchase may already have happened in the Jarvis work — check before buying another.)
- **Environment variables:**

```
DATABASE_URL
AGENT_SERVICE_TOKEN
NEXTAUTH_SECRET / AUTH_GOOGLE_ID / AUTH_GOOGLE_SECRET
ALLOWED_EMAILS            # comma-separated, exact addresses
SLACK_BOT_TOKEN / SLACK_SIGNING_SECRET
VERCEL_API_TOKEN / VERCEL_TEAM_ID
GSC_SERVICE_ACCOUNT_JSON  # or OAuth refresh token
QBO_CLIENT_ID / QBO_CLIENT_SECRET / QBO_REFRESH_TOKEN / QBO_REALM_ID
VAULT_SYNC_TOKEN
```

## 6. Build order

Phased so each phase is independently useful and the riskiest write path comes last. Do not start a phase before its predecessor's acceptance checks pass.

### Phase 0 — Schema and a one-shot vault import
Migrations for all six tables. A CLI script that walks the vault once and upserts `clients` from frontmatter. No watcher, no UI.
**Accept when:** every client note parses into a row, and a note with deliberately broken YAML fails loudly with a filename instead of corrupting a row.
**Why first:** it surfaces missing frontmatter keys in the client template immediately, while fixing them is cheap.

### Phase 1 — Read-only views
Client list, client drill-down, run history, health flags. Cron fetchers for Vercel, GSC, uptime, QBO writing `metric_snapshots`. Auth on. Deploy to Vercel.
**Accept when:** every tile shows a source and an as-of timestamp; a client with no `gsc_property` renders grey rather than green; killing a fetcher for an hour degrades tiles visibly instead of blanking them.
**Why here:** read-only cannot break anything the agents depend on, and it is the fastest path to something Nick and Cam open daily.

### Phase 2 — Locks and the agent SDK
Lock endpoints, TTL, heartbeat, ownership-checked release, stale reclamation with an alert. A shared client library every agent calls — acquire, heartbeat, release in a `finally`.
**Accept when:** two agents launched simultaneously against one client produce exactly one worker and one `skipped_locked` run; a killed agent's lock expires and is reclaimed within its TTL with a Slack alert; a resumed zombie cannot release a newer run's lock.
**Why here:** first write path, agents-only, no human-facing consequence if it misbehaves during shakedown.

### Phase 3 — Approvals
Approval creation from agents, queue UI with approve / reject / approve-with-edits, Slack posting with buttons, signature-verified interactions endpoint, `chat.update` on decision, retry worker, reconciliation cron, expiry sweep.
**Accept when:** an approval survives Slack being unreachable at post time and at click time; double-clicking Approve produces one transition; an expired item lands in the queue flagged and unsent; rejecting without a reason is rejected by the database.
**Why here:** it is the highest-consequence path — a bug sends a client email twice — so it goes after the infrastructure it depends on is proven.

### Phase 4 — Write-back to the vault
Render execution logs into `AGENTS/Execution-Logs/` with the collision-safe filename, and regenerate the roster tables in `CLIENTS/00-Active-Clients.md` from client frontmatter.
**Accept when:** write-back never produces a Dropbox conflicted copy under normal operation, writes are atomic (temp file + rename), and a failed write is retried rather than half-applied.
**Why last:** writing into a Dropbox-synced folder that a human also edits is the riskiest operation in the whole system, and it is worth nothing until the data it writes is trustworthy.

### Later, only if wanted
Client-facing report portal; cost tracking per agent run through the AI gateway; mobile layout (Slack likely covers approvals-on-the-go already).

## 7. Non-goals

- Not a client-facing portal.
- Not a human task manager.
- No clinic or patient data.
- No custom auth, no multi-tenant permissions, no roles beyond "Nick and Cam."
- No real-time revenue. Revenue moves on invoice-and-payment timelines; see [[01-Live-Metrics]] Tier 4.
